# Датчики таймеров и будильников Custom-Dialog-UI

## Формат в 0.3.7

Атрибут `payload` — **нативный массив объектов Home Assistant**, даже для одной
записи. Это не строка JSON, не словарь по именам устройств и не объект-обёртка.
Устройство и клиент определяются по полям внутри записи. Пустой массив — `[]`.

`sensor.dialog_custom_ui_timers` считает устройства с оставшимися таймерами.
Для каждого устройства публикуется последний созданный оставшийся таймер:

```yaml
payload:
  - id: c3ff878d-33a7-4adc-99cc-6f5210fcdef0
    media: media_player.home_assistant_voice_0ab77d_media_player_2
    client_id: voice-client
    device_id: f78b84553b463617269c25293950bb55
    total_seconds: 300
    remaining_seconds: 293
    paused: false
_updated_at: 1791806675
```

`_updated_at` — отдельный атрибут датчика, обновляемый примерно раз в секунду,
включая паузу и отсутствие таймеров. Работающий остаток уменьшается, на паузе
стоит. Исходная длительность сохраняется; `paused` нужен для индикации паузы,
`id` — для определения смены таймера. После завершения или удаления нового
таймера публикуется предыдущий оставшийся таймер этого устройства. После
удаления всех состояние `0`, `payload: []`, heartbeat продолжается.

`sensor.dialog_custom_ui_alarm` — информационный датчик:

- `on` — есть хотя бы один включённый будильник;
- `off` — включённых будильников нет;
- `active_count` — количество включённых будильников.

Он публикует все установленные будильники, включая отключённые:

```yaml
active_count: 1
payload:
  - id: alarm-uuid
    media: media_player.home_assistant_voice_0ab77d_media_player_2
    client_id: voice-client
    device_id: f78b84553b463617269c25293950bb55
    status: "on"
  - id: another-alarm-uuid
    media: media_player.other_column
    client_id: another-client
    device_id: another-device-id
    status: "off"
```

`on` означает наличие включённого запланированного будильника, а не проигрывание
звука в данный момент. Чтение датчиков не создаёт записи, не запускает таймеры
или будильники и не воспроизводит сигнал.

## Сопоставление устройства и медиа

`device_id` — канонический ID устройства из реестра HA. Если таймер создан через
`media_player`, его связь с устройством разрешается через `entity_registry`.
Если связь неизвестна, сохраняется исходная ссылка; устройство не угадывается.
Таймеры разных колонок остаются отдельными записями. На одной колонке голосовой
device ID и entity ID из интерфейса объединяются перед выбором нового таймера.

`media` — доступный проигрыватель этого устройства. Явный `media_player` сохраняет
приоритет. Отключённые, отсутствующие и недоступные проигрыватели исключаются.
Если доступных кандидатов несколько или подходящих нет, `media` равно `""`.
Датчик не выбирает другую колонку и не пишет повторяющиеся предупреждения
каждую секунду. Реальные попытки воспроизведения сохраняют диагностику в журнале.

Если ручной выбор Voice PE работает, а голосовой device ID нет, проверьте:

```jinja2
{{ device_entities('f78b84553b463617269c25293950bb55') }}
{% for player in states.media_player %}
{{ player.entity_id }} — {{ player.name }} — {{ device_id(player.entity_id) }}
{% endfor %}
```

При двух доступных проигрывателях одного устройства передавайте конкретную
рабочую сущность в YAML-сервис. `timer_create` и `alarm_create` принимают оба
варианта `deviceId`/`device_id`; разные значения одновременно отклоняются.
Голосовой payload использует `device_id`, изменять его имя не нужно.

## Сохранение и время

Хранилища сохраняют исходные UUID, `client_id`, время создания, исходную
длительность, остаток, срок окончания и паузу. Обновления и возобновление не
меняют порядок создания. После восстановления применяется сохранённый клиент,
а не общий ID из настроек. Для старых записей без `client_id` остаётся прежний
резервный вариант — клиент из настроек либо пустая строка. Потерянные ранее
клиент, время создания, паузу и исходную длительность нельзя восстановить
достоверно. Голосовое создание не добавляет вторую запись с отдельным UUID.

Завершённый таймер удаляется и датчики уведомляются до звука и пользовательского
сценария; их задержки не блокируют публикацию оставшегося таймера. Сигналом
окончания управляет интеграция. Локальный файл по умолчанию `timer-alarm.mp3`
должен существовать в медиа-каталоге HA; в репозитории его нет. Громкость
восстанавливается после воспроизведения, готовые HTTP/media-source URL сохраняются.

«Установи таймер на 1 минуту» создаёт 60 секунд. `date_end` сохраняется в ISO 8601
с UTC-смещением: часовой пояс не прибавляется к длительности на фронтенде.
«Заведен на» показывает исходную длительность, заголовок карточки — остаток.

## Обновление и потребители данных

Обновите всю папку `custom_components/dialog_custom_ui`, проверьте версию
`0.3.7` в manifest и полностью перезапустите HA. Для HACS нужен коммит/релиз,
содержащий изменения; локальный manifest сам по себе не публикует релиз HACS.
Обновите страницу интерфейса. Не удаляйте `.storage` и не создавайте сущности
через `/api/states`. Существующие unique ID сохранены. Если датчик переименован
или отключён, проверьте список сущностей интеграции.

**Контракт payload изменён по сравнению с 0.3.6.** Потребителям старой строки JSON
с ключами device ID/ESPHome name нужна адаптация. Новое чтение: перебрать массив,
выбрать запись по `device_id` (или `media`), читать её поля. Для heartbeat читать
отдельный атрибут `_updated_at`. Прошивка Voice PE, рассчитанная на старый формат,
не совместима автоматически: её адаптация не выполнена в этом репозитории.

Пример шаблона HA для выбора устройства — без `from_json`:

```jinja2
{% set records = state_attr('sensor.dialog_custom_ui_timers', 'payload') or [] %}
{{ records | selectattr('device_id', 'eq', 'f78b84553b463617269c25293950bb55') | list }}
```

## Проверки

Тесты используют локальное ядро HA 2025.1.4 на Python 3.12, реальные SensorEntity,
реестры и хранилища. Проверяются формы длительности, порядок и пауза, завершение,
две колонки, переход между entity/device ID, два голосовых таймера, клиент и UUID
после восстановления, объектный payload обоих датчиков, отключённые будильники,
выгрузка и перезапуск. Установка пользователя и физический Voice PE недоступны
для автоматической проверки; на устройстве требуется проверить новый потребитель
payload, независимость колонок, паузу больше 15 секунд и отсутствие двойного звука.

```sh
UV_CACHE_DIR=/workspace/.uv-cache /workspace/ha-venv/bin/python -m pytest tests -q --asyncio-mode=auto
TZ=UTC node --test tests/test_timer_frontend.mjs
TZ=Europe/Moscow node --test tests/test_timer_frontend.mjs
TZ=Asia/Yekaterinburg node --test tests/test_timer_frontend.mjs
```

Фронтенд требует Node.js 24 и `npm ci`. Для проверки сборки без изменения
отслеживаемых файлов: `npm run build -- --outDir /tmp/dialog-frontend-check`.
Изолированная среда уже содержит checkout; отдельный Git worktree не требуется.

## Передача в ESPHome

Атрибут `payload` остаётся списком для интерфейса и автоматизаций. Для подписки
ESPHome используйте `payload_json` обоих датчиков: это JSON-строка с теми же
записями. Home Assistant передаёт обычный список в ESPHome через `str(list)`,
поэтому `payload` не подходит для JSON-парсера прошивки.
Обновите интеграцию, перезапустите Home Assistant, затем обновите прошивку.
