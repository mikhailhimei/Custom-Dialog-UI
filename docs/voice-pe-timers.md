# Таймеры на кольце Home Assistant Voice PE

Обновите Custom-Dialog-UI и перезапустите Home Assistant. Интеграция создаёт
датчик `sensor.dialog_custom_ui_timers`. Его атрибут `payload` содержит JSON
последнего оставшегося таймера каждого устройства и обновляется раз в секунду.
Таймер выбирается по времени создания, а не по UUID или времени до окончания.
Время создания сохраняется вместе с таймером в JSON.

Обновите прошивку Voice PE из ветки `dev` репозитория
`mikhailhimei/home-assistant-voice-pe`. По умолчанию прошивка читает этот датчик
через API Home Assistant. Интеграция сопоставляет `deviceId` таймера с именем
ESPHome через реестр устройств, поэтому вручную указывать ID обычно не нужно.
Подключение ESPHome в Home Assistant должно быть доступно.

Если датчик получил другое имя (например, при нескольких экземплярах интеграции),
укажите его в YAML колонки:

```yaml
substitutions:
  dialog_timer_entity: sensor.dialog_custom_ui_timers_2
```

Если таймер использует нестандартный идентификатор устройства, можно указать
точное значение `deviceId` из JSON таймера:

```yaml
substitutions:
  dialog_timer_device_id: "идентификатор устройства"
```

Во время ожидания команды кольцо показывает обычную анимацию помощника.
В свободном состоянии оно показывает долю оставшегося времени таймера.
Пауза замораживает прогресс. При удалении или окончании последнего таймера
отображается предыдущий оставшийся; если их нет, кольцо возвращается в обычное
состояние. Через 15 секунд без обновлений датчика индикация внешнего таймера
сбрасывается. Штатные таймеры ESPHome работают, когда нет внешнего таймера.

Сигнал окончания по-прежнему запускает Custom-Dialog-UI; прошивка не дублирует его.

Проверка на устройстве: создайте длинный таймер, затем короткий на той же колонке.
Кольцо должно показывать короткий; удалите его — должен появиться длинный.
Поставьте последний таймер на паузу и убедитесь, что кольцо перестало уменьшаться.
Таймер другой колонки не должен менять кольцо этой.

## Обновление и диагностика отсутствующего датчика

1. Сделайте резервную копию конфигурации Home Assistant. Установите **всю**
   обновлённую папку `custom_components/dialog_custom_ui` в каталог конфигурации
   работающего Home Assistant. Недостаточно обновить только `sensor.py` или
   JavaScript интерфейса. В этой версии `manifest.json` содержит `0.3.5`.
   Для HACS понадобится версия/коммит, содержащий эти изменения; изменение
   локального manifest само по себе не публикует релиз HACS.
2. Полностью перезапустите Home Assistant: Python-модули и список платформ
   загружаются в процесс, обновление страницы браузера их не заменяет.
3. В «Настройки → Устройства и службы» убедитесь, что экземпляр Dialog Custom UI
   добавлен, включён и загружен. Датчик создаётся при загрузке **config entry**, даже
   без таймеров. Одного наличия папки или YAML-записи недостаточно.
4. В списке сущностей интеграции включите датчик, если он отключён пользователем.
   Проверьте также переименованную сущность или суффикс `_2`: существующий
   `unique_id` сохранён, чтобы обновление не создавало дубликат и не отменяло
   пользовательское имя.
5. В «Инструменты разработчика → Состояния» проверьте
   `sensor.dialog_custom_ui_timers`: без таймеров состояние `0`, а строка `payload`
   содержит только `_updated_at`. Через несколько секунд метка должна измениться.
   Проверка через шаблон:

   ```jinja2
   {% set raw = state_attr('sensor.dialog_custom_ui_timers', 'payload') %}
   {{ raw is string }}
   {{ (raw | from_json)['_updated_at'] if raw is string else 'нет payload' }}
   ```

6. Если сущности всё ещё нет, проверьте журнал `dialog_custom_ui`,
   `homeassistant.config_entries` и `homeassistant.components.sensor`: ошибки
   импорта, установки зависимостей, восстановления и запуска до forwarding
   платформ не позволяют создать датчик. Исправьте указанную в журнале причину
   и перезагрузите интеграцию или Home Assistant. Не удаляйте `.storage`, не
   создавайте сущность вручную через `/api/states` и не добавляйте второй датчик.

В исходном проверенном `main` платформа `sensor` уже была зарегистрирована.
Её отсутствие на установленном экземпляре не воспроизведено: исходный датчик
создался на локальном ядре Home Assistant 2025.1.4. Поэтому без журнала и проверки
установленных файлов нельзя утверждать, что причиной была регистрация платформ.
Номер версии при первоначальном добавлении датчика оставался `0.3.3`, что также
не позволяло отличить старую установленную папку от обновлённой по manifest.
Исправленная версия сохраняет штатный датчик и его идентификатор, обрабатывает
отказ выгрузки и очищает менеджер при исключении загрузки для повторной попытки.

## Формат и сохранение

Состояние считает устройства, а не таймеры или JSON-ключи. Ссылки на entity и
registry device одного устройства объединяются. Строка `payload` выглядит так:

```json
{
  "_updated_at": 1791740000,
  "home-assistant-voice-0ab77d": {
    "id": "timer_uuid",
    "created_at": 1791739940,
    "total_seconds": 120,
    "remaining_seconds": 60,
    "paused": false
  },
  "исходный-deviceId": {
    "id": "timer_uuid",
    "created_at": 1791739940,
    "total_seconds": 120,
    "remaining_seconds": 60,
    "paused": false
  }
}
```

Ключ ESPHome берётся из `config_entry.data.device_name`, после разрешения
`deviceId` через `entity_registry` и `device_registry`. Если одинаковое имя
принадлежит нескольким устройствам, автоматический alias не публикуется:
используйте исходный `deviceId` или исправьте неоднозначные имена. Остальные
колонки продолжают получать свои таймеры. Неизвестный `deviceId` остаётся только
ручным ключом, без попыток угадать устройство по похожему имени.

JSON-хранилище `.storage/dialog_custom_ui_timer_requests` сохраняет `status`,
`timer_time.created_at`, `total_seconds`, `remaining_seconds` и `date_end`.
Работающий таймер восстанавливается до сохранённого срока окончания, а не на
полную длительность. Истёкший во время выключения таймер не запускается заново
и не проигрывает запоздалый сигнал. Пауза восстанавливается с сохранённым
остатком, без учёта времени выключения. Обновление, пауза и возобновление
сохраняют время создания и исходную длительность; редактирование интервала
меняет остаток. Чтение датчика и списка интерфейса не запускает таймеры.

В старых записях без `created_at` исторический порядок восстановить невозможно:
при первой загрузке используется порядок записей хранилища и сохраняются новые
метки. Уже потерянные старой версией исходная длительность или пауза также не
могут быть восстановлены достоверно. Новые записи сохраняют эти данные.

## Автоматические проверки и проверки устройства

Автоматические тесты используют настоящее ядро Home Assistant **2025.1.4** на
Python **3.12**, реальные `SensorEntity`, реестры, сервис и JSON-хранилище.
Это отдельный локальный экземпляр, а не установленный Home Assistant пользователя.
Тесты проверяют:

- выбор самого нового таймера независимо от UUID и остатка;
- уменьшение остатка, паузу и возобновление;
- удаление, завершение, возврат предыдущего таймера и один вызов звука;
- независимость колонок, объединение entity/device ссылок, отказ от неоднозначного alias;
- сохранение UUID, порядка, исходной длительности и паузы при восстановлении;
- голосовое создание, синхронизацию интерфейса и `dialog_custom_ui.timer_create`;
- отсутствие перезапуска при чтении и сохранении другого таймера;
- реальное создание датчика, секундный heartbeat на паузе и без таймеров;
- обработку исключения forwarding, повторную загрузку и отказ выгрузки;
- новый экземпляр ядра после остановки: загрузку сохранённого датчика и таймера
  без дубликата сущности.

Запуск из корня репозитория после установки зависимостей manifest и
`tests/requirements.txt`:

```sh
UV_CACHE_DIR=/workspace/.uv-cache /workspace/ha-venv/bin/python -m pytest tests -q --asyncio-mode=auto
```

Сборка фронтенда не нужна для этих изменений Python. Тесты завершают запущенные
ими экземпляры HA; постоянный сервер или отдельный Git worktree не требуется.

На установленном Home Assistant и физическом Voice PE дополнительно проверьте:

1. Появление сущности после **полного перезапуска**, строковый JSON и изменение
   `_updated_at` раз в секунду. Убедитесь, что alias совпадает с ESPHome
   `device_name`, а прошивка подписана на фактический entity ID.
2. Создайте длинный таймер, затем более длинный новый на той же колонке — кольцо
   должно выбрать именно новый. Проверьте голос, интерфейс и сервис отдельно:

   ```yaml
   action: dialog_custom_ui.timer_create
   data:
     clientId: ваш_client_id
     deviceId: идентификатор_из_реестра_или_entity_id
     mm: 2
   ```

3. Пауза более 15 секунд должна заморозить прогресс без сброса индикации;
   возобновление продолжает отсчёт. Вторая колонка показывает только свои таймеры.
4. Удаление и окончание нового таймера возвращают предыдущий; удаление всех
   убирает записи устройства. Убедитесь, что звук окончания не дублируется.
5. Перезапустите Home Assistant с двумя таймерами, один из них на паузе:
   проверьте порядок, исходные длительности и сохранённую паузу. Проверьте сброс
   индикации прошивкой через 15 секунд после прекращения обновлений.

Доступ к установленному Home Assistant пользователь не предоставил. Проверка
физической индикации, доставки данных через ESPHome API, звука на колонке и
совместимости с фактической версией HA остаётся обязательной проверкой на устройстве.

## Голосовой таймер виден, но звук отсутствует

Карточка показывает исходный `device_id`, если он является ID устройства, а
интерфейс знает только названия проигрывателей. Это не результат преобразования:
целевой `media_player` разрешается через реестры в момент воспроизведения.
Сохранённая карточка сама по себе не подтверждает запуск отсчёта; интерфейс
читает JSON-хранилище и считает оставшееся время локально.

Если ручное создание с выбором Voice PE воспроизводит звук, сравните голосовой
ID с ID устройства проигрывателя в «Инструменты разработчика → Шаблоны»:

```jinja2
Голосовое устройство:
{{ device_entities('f78b84553b463617269c25293950bb55') }}
Проигрыватели и их ID устройств:
{% for player in states.media_player %}
{{ player.entity_id }} — {{ player.name }} — {{ device_id(player.entity_id) }}
{% endfor %}
```

У голосового ID должна быть сущность проигрывателя именно нужной колонки.
Пустой список или другой ID у Voice PE означает отсутствие нужной связи в
реестре; произвольный `application_id` не обязательно является HA device ID.
Нельзя безопасно угадать колонку по этому значению или выбрать первый
проигрыватель из общего списка. В YAML-скрипте можно явно передать проверенный
`media_player` нужной колонки в `dialog_custom_ui.timer_create`/`alarm_create`.
Поля `deviceId` и `device_id` теперь принимаются обоими сервисами; при разных
значениях одновременная передача обоих полей отклоняется. Голосовой payload
использует `device_id`, и менять его формат на `deviceId` не требуется.

Общий путь звука таймеров и будильников принимает HA device ID, entity ID
проигрывателя или другой entity ID того же устройства. Отключённые, отсутствующие
и недоступные проигрыватели не выбираются. Если доступных проигрывателей одного
устройства несколько, укажите нужный `media_player` явно. Предупреждения в
журнале различают неизвестный device ID, отсутствие проигрывателя, его
недоступность и неоднозначный выбор. Ошибка `play_media` записывается вместе с
целевым entity ID и аудиофайлом.

Также исправлены преждевременный возврат громкости (при исходной громкости `0`
он мог заглушить сигнал) и повторное оборачивание готового HTTP/media-source URL.
Начальная громкость устанавливается до воспроизведения, предыдущая
восстанавливается после его окончания. Локальный файл по умолчанию
`timer-alarm.mp3` должен существовать в медиа-каталоге HA; он не включён в
репозиторий. Дополнительные тесты проверяют разрешение устройства и сущностей,
изоляцию колонок, оба варианта поля сервиса, вызов звука, ошибки проигрывателя,
готовые URL и порядок изменения громкости. Фактическая связь ID из голосового
payload с пользовательской колонкой требует результата шаблона выше.


## Длительность и часовой пояс (0.3.5)

Фраза «Установи таймер на 1 минуту» разбирается как 60 секунд. Формы «минуту»
и «секунду», сокращения и смешанные длительности учитываются до эвристик
часового времени. Время будильника с маркером «утра»/«вечера» продолжает
разбираться как время суток.

`date_end` теперь сохраняется в ISO 8601 с явным UTC-смещением. Фронтенд
вычитает абсолютные моменты времени и не прибавляет часовой пояс к длительности.
Для старого значения без смещения используются числовой остаток или длительность,
без попытки угадать зону браузера. На карточке «Заведен на» показывает исходную
длительность, заголовок — остаток. У паузы используется сохранённый остаток.
Старые таймеры, уже ошибочно созданные на час, автоматически не сокращаются:
удалите их и создайте заново после обновления.

Сборка `static/dialog-custom-ui-panel.js` обновлена вместе с исходниками.
После установки 0.3.5 перезапустите HA и обновите страницу интерфейса, чтобы
получить новый JavaScript. Для проверки создайте голосом минутный таймер и
ручной часовой: длительности должны быть `00:01:00` и `01:00:00` соответственно,
независимо от зоны браузера.

Проверки фронтенда (Node.js 24):

```sh
TZ=UTC node --test tests/test_timer_frontend.mjs
TZ=Europe/Moscow node --test tests/test_timer_frontend.mjs
TZ=Asia/Yekaterinburg node --test tests/test_timer_frontend.mjs
npm run build
```

Команда сборки обновляет отслеживаемый статический файл. Для проверки среды без
изменения репозитория используйте `npm run build -- --outDir /tmp/dialog-frontend-check`.
